# Local setup and build process

Prerequisites: Node 22+, pnpm 11.25.0, Docker Compose v2. Run from the existing checkout; cloud tasks are already isolated and need no worktree.

```bash
cp .env.example .env
# Local development password only; use a secure generated value outside local development.
export POSTGRES_PASSWORD=local_dev_only
export DATABASE_URL=postgresql://automotive:local_dev_only@localhost:5432/automotive
pnpm install --frozen-lockfile
docker compose up -d --wait
pnpm db:generate
pnpm db:migrate
pnpm db:seed
pnpm typecheck
pnpm test
pnpm build
pnpm dev
```

Ports: customer 3000, admin 3001, API 4000. API `/health` is liveness; `/docs` is Swagger. Export variables in the invoking shell: a root `.env` alone is not automatically loaded by every workspace command. No credentials are needed for public development catalog reads. Protected API operations require a configured OIDC provider and a provisioned tenant user.

In the cloud runner the home directory may be read-only. Use `XDG_DATA_HOME=/workspace/.local/share XDG_CACHE_HOME=/workspace/.cache` and `pnpm --store-dir /workspace/.pnpm-store install --frozen-lockfile`.

Build shared packages first via Turborepo dependencies; TypeScript checks NestJS and shared modules, while Next.js builds customer/admin applications. Prisma schema changes require a new reviewed migration; never use `db push` in production. Seed is development-only and idempotent.

### Migration implementation

Prisma 6.19's experimental JavaScript migration adapter cannot deserialize PostgreSQL `name` metadata during `migrate deploy` in this environment. `pnpm db:migrate` therefore applies the Prisma-generated SQL using a transaction, an advisory lock and the `_xr_migrations` SHA-256 journal. Do not mix it with Prisma CLI migration deployment on the same database. Initial SQL was generated by `prisma migrate diff` using the WASM schema engine. Migration files are immutable after application. The current runner supports ordinary semicolon-delimited DDL; procedural SQL requires extending the runner first.

## Interactive local sign-in

After database setup and building shared packages, run `pnpm dev:local` from the checkout. This launches web/admin/API development processes plus a loopback-only development OIDC issuer on port 5010. Sign in as the explicitly labelled customer or tenant admin. It provisions only the seeded development tenant's identities and stores a generated sharing key under ignored `.local/`. No production password or signing key is shipped.

For a real provider use `pnpm dev` with `OIDC_ISSUER`, `OIDC_AUDIENCE`, `NEXT_PUBLIC_OIDC_ISSUER`, `NEXT_PUBLIC_OIDC_CLIENT_ID` and a private `SHARE_SIGNING_KEY` configured. Tokens must contain the verified tenant UUID claim and the subject must already have tenant membership. Do not run the local identity fixture on a public machine. Changes to a shared package need a package rebuild before its consuming app picks up generated output.

## Tests

`pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm test`, `pnpm build`. With PostgreSQL and Redis running, use `pnpm test:integration`. Browser tests start their own API/identity/web/admin processes; keep ports 3000, 3001, 4000, 5010 free. Build with `NEXT_PUBLIC_OIDC_ISSUER=http://127.0.0.1:5010 NEXT_PUBLIC_OIDC_CLIENT_ID=automotive-xr-local pnpm build`, then run `CHROMIUM_PATH=/usr/bin/chromium pnpm test:e2e` when system Chromium is installed, or install Playwright Chromium and omit that variable. Use a disposable seeded development database: browser tests create configurations, leads and archived catalog records under the development tenant. API integration fixtures are removed after their run.

Cloud activation also sets `XDG_CONFIG_HOME=/workspace/.config`, adds `/workspace/.local/share/pnpm/bin` to `PATH`, and stores the pnpm cache setting in that writable global config. Use `bash scripts/cloud-setup.sh` to initialize these settings and dependencies. For later shells export those XDG paths and PATH before invoking pnpm.
